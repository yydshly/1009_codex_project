016 / 能力 · 模块 · 原理 · 价值 · 扩展

Agenvo 理解指南

Agenvo 是一个自托管 MCP 中继。它把你的助手接到电脑或服务器上的 Codex、Herdr 中的 Claude Code 等原生运行时，让助手远程查询、下达指令、读取结果并继续推进工作。

完整摘要

一眼读懂 Agenvo

先看定位与价值，再沿目录了解实现细节。

定位
远程 Agent 接入层。自托管 MCP 中继，让通用助手连接 Codex、Herdr 中的 Claude Code 等原生 Agent。
能力
发现、发任务、看结果、继续与中断。还可响应原生交互请求、订阅变化；具体动作取决于各运行时。
模块
客户端 → Relay → Connector / Adapter → 原生 Agent。客户端做决策，Relay 管连接与授权，内置 Adapter 转接原生接口，Agent 执行。
原理
通过配置与原生 ID 找到目标。Connector 主动连接 Relay；按 deviceId / instanceId 找 Adapter，再按 threadId、session / name 等找到会话。
部署
通常一个 Relay，目标侧按运行时安装 Connector。Adapter 随包提供；每个任务或聊天无需单独部署。Agent 和模型认证需自行准备。
价值
跨 Agent 统一入口，复用接入基础设施。适合自建助手、自动化与二次开发；只为手机继续用 Codex，新增价值有限。
边界
单所有者；没有统一任务调度器或业务成功判定。脚本隔离不等于 Agent 执行隔离；Relay 可见流量。本站未独立实测原生 Agent。
扩展
连接与证据面板、客户端验收、新运行时适配、任务编排、故障恢复、细粒度权限。这些是我们的建议，尚待设计或验证。

02 / WHAT IT DOES

把远处的 Agent，变成助手可调用的工具

人说目标，助手选择运行位置和原生方法。可用动作取决于对应运行时，能力不会因为接入 MCP 就自动一致。

01

发现与选择

列出获准实例，查看在线状态、原生方法、执行环境说明，选择电脑与运行时。

search · instance context
02

创建与发任务

创建 Codex thread，或在 Herdr pane 启动 Agent，再把提示词送入原生工作上下文。

thread/start · agent.start
03

看进展与结果

读当前状态、原生输出、可用历史或终端快照，判断实际工作进度。

thread/read · agent.read
04

继续与纠偏

恢复会话、追加指令、调整活跃轮次，按运行时提供的能力继续处理。

thread/resume · turn/steer
05

回答与中断

处理用户问题与工具请求，或请求停止。Codex 的精确 turn 中断与终端按键语义不同。

requests.respond · turn/interrupt
06

变化后再跟进

支持事件的 MCP 客户端收到变化后，再读状态、解释结果并决定下一步。

runtime.changed
“协调”发生在上层助手。

Agenvo 没有独立业务任务队列、统一完成判定或自动任务调度器。跨 Agent 分工、重试策略、结果验收由调用方实现。

03 / WHO OWNS WHAT

四个角色，三类状态

适配器是 Connector 里的代码。Relay 是你自托管的公网服务；目标电脑只需主动向它建立连接。

A

客户端 / 上层 AI 助手

接收目标，通过 MCP 发现方法与调用工具；决定任务放在哪里、何时再观察、是否继续或取消。

决策与工作流
B

Relay / 自托管中继

提供 HTTPS MCP、OAuth、管理页、配对与授权；管理 Connector 连接、关联请求结果、执行短脚本、投递事件。

授权与连接状态
C

Connector + 内置 Adapter

通常运行在目标电脑，主动 WSS 连接 Relay。每个配置实例创建一个 Adapter，按实例 ID 分发并翻译成原生调用。

原生连接与桥接
D

真实 Agent / 原生运行时

Codex app-server、Herdr、Paseo daemon 等使用自己的身份、模型凭据、项目、工具、权限与会话历史执行工作。

任务与会话状态
源码模块与职责
模块职责不负责的部分
packages/protocol消息类型、校验、地址、限制、OutcomeAgent 决策与原生任务状态
packages/connectorCLI、配置锁、配对、WSS、心跳重连、调用分发、状态文件通用 AI 推理与各平台内部任务库
packages/relayMCP search/execute、QuickJS、授权、请求关联、管理页面、事件、版本提示替代原生会话与业务验收
apps/codex-app-server 等各自配置 schema、原生方法与连接、错误语义、事件桥接强行统一不同运行时的全部语义
apps/cloudflareWorkers + Durable Objects SQLite + 可休眠 WebSocket跨宿主自动迁移
apps/server单 Node 进程 + SQLite + HTTP/WS + OAuth；HTTPS 由代理或 TLS 提供多副本集群与网络文件系统部署

Relay 核心通过 RecordStore / RelayHost / RelaySocket 接口复用。后端经静态 Backend 接口接入共享 Connector，没有动态插件扫描加载。

04 / FOLLOW ONE REQUEST

一条指令，如何找到真实的 Agent？

用“让服务器上的 Codex 修复测试”走一遍路径。按下面六步阅读各层的职责与关联方式。这是源码流程说明，未连接真实 Agent。

  1. 01

    客户端 → Relay → Connector

    发现可用实例与原生方法

    动作
    助手通过 MCP 调用 search，发现获准实例，以及该运行时提供的方法。
    发现规则
    按运行时类型、方法名、描述做关键词 AND 匹配；空 query 只列实例。完整参数需 includeSchema: true。
  2. 02

    助手选择实例与会话

    取得目标的原生身份

    目标
    用 deviceId + instanceId 选中服务器上的 Codex 配置。实例 context 帮助选择环境。
    会话
    新任务先调用 thread/start 并保留原生返回的 threadId；继续旧会话则查询并按需 resume。
  3. 03

    客户端 → HTTPS /mcp → Relay

    中继找到当前 Connector 连接

    提交
    助手用 execute 运行短脚本，调用原生方法，例如 turn/start 提交“修复测试”。
    关联
    Relay 检查授权、实例范围与在线连接，记录 requestId 和连接代次，再通过对应 Connector 的 WSS 发送。
  4. 04

    Relay → 目标侧 Connector

    内置 Adapter 接到这次调用

    分发
    Connector 校验消息、重复请求、获准范围与可用性，按 instanceId 取出启动时创建的 Adapter。
    转交
    调用 adapter.call(method, params)。Adapter 是进程内对象，无须另装一个服务；Relay 也不用扫描进程猜目标。
  5. 05

    Codex Adapter → 独立 app-server

    原生接口定位具体工作上下文

    接口
    Adapter 校验原生 schema，通过已初始化的本机 WebSocket / Unix socket 发送 JSON-RPC；当前 Connector 不启动 Codex 进程。
    原生路由
    threadId 找到会话，RPC id 匹配应答，返回的 turnId 用于观察或中断本轮执行。
  6. 06

    原生结果 → Connector → Relay → 助手

    读取进度，验证实际结果

    应答
    原生 RPC 应答经 Adapter 返回；Relay 用 requestId 匹配等待项，再次检查授权与连接代次，交付脚本所选内容。
    跟进
    助手在收到变化或稍后发起新调用，读取状态、输出、测试和产物。accepted 只表示接受输入；unknown 时先查证，再考虑重试。
标识找到什么关键区别
deviceId一份已配对 Connector不是物理电脑 ID；同机多个 Connector 有多个身份
instanceIdConnector 内的一项运行时配置和 Adapter不是每一个任务；一个实例可有许多会话
threadId / turnIdCodex 原生会话 / 本轮执行由 Codex 返回；steer / interrupt 按原生字段定位
session / name / paneIdHerdr 服务 / Agent 名称 / 终端窗格名称与 ID 可能复用；不能当作永久会话身份
requestId / RPC idAgenvo 调用 / 原生 JSON-RPC 请求关联两层应答，不代表业务任务 ID
fingerprint / epoch获准实例范围 / 当前连接代次防范围变化与旧连接结果串入；不提供任务级幂等
资料依据
Relay 请求关联 ↗ adapters.get(instanceId) 分发 ↗

05 / NATIVE INTEGRATIONS

Codex 是技术接口，Claude Code 经原生管理器接入

不同 Adapter 使用不同接入方式。Agenvo 依赖已有原生能力，把网络、授权、发现和调用链补齐。

CodexHerdr / Claude Code其他运行时
原生双向 JSON-RPC

先独立运行 app-server，Connector 再连接

连接方式
Unix socket 上的 WebSocket，或 loopback WebSocket。Windows 使用 loopback；Connector 不启动或停止 Codex 进程。
初始化
initialize → initialized，核对服务报告的 codexHome 与配置。
请求关联
生成 RPC id、记录 pending，按应答 ID 匹配；通知与待响应请求分别处理。
原生会话
thread/start 创建会话；turn/start 带 threadId 提交输入。未加载的会话先 resume；返回 turnId 用于后续定位。

当前 Windows / loopback 路径示例

# 原生服务：由另一个终端或服务管理器持有
codex app-server --listen ws://127.0.0.1:4500

# Connector 指向已存在的 home 和服务
agenvo-codex-app-server instance add --id coding --home "C:\Users\you\.codex" --endpoint ws://127.0.0.1:4500 --cwd "C:\repo"

说明性示例：请替换 home 和项目路径。Connector 要求 Node.js 24.13+；服务由另一个终端或服务管理器持有。

桌面 App 的已有聊天不会自动被接管。

Connector 共享的是所连接端点可访问的会话。另开 app-server 是另一个服务；桌面 stdio 进程没有自动提供兼容监听端点。原生 stdio 接口仍存在，但当前 Agenvo Codex Connector 使用附着模式。

权限
创建、恢复、输入使用 full access / never；原生执行权限请求自动回答。用户问题与动态工具调用仍需提供内容。
兼容
原生 schema 含 experimental 能力；发现到方法，不代表所有版本都能使用。
记录
通知是连接内的有界缓存；历史读取取决于原生服务支持。
资料依据
连接与 RPC ↗ Codex 设计与验证边界 ↗ 官方 App Server 接口 ↗
原生 CLI + Socket 事件

用 session 找服务，用 name / paneId 找 Agent

原生服务
Herdr 是独立运行的终端 Agent 管理服务，可管理 Claude Code、Codex 等。
发现目标
Agenvo 附着实际配置目录，发现 default 与 sessions 服务，也能发现外部客户端创建的 Agent。
执行调用
主要执行 Herdr CLI：agent.prompt 转为 herdr agent prompt NAME TEXT，环境变量指向正确服务。事件直接订阅原生 socket。
启动进程
agent.start 在已有 pane 启动，由 Herdr 判断 kind。args 原样转发；当前 Agenvo 不维护类型白名单，也不注入固定权限参数。

绑定原生 Herdr 服务

HERDR_SOCKET_PATH = session 对应的 socket
HERDR_CONFIG_PATH = configRoot/config.toml
XDG_CONFIG_HOME   = configRoot 的父目录
HERDR_SESSION    = 当前原生 session

agent.prompt({ session, name, text })
→ herdr agent prompt NAME TEXT
→ 原生服务 → 对应 pane 里的 Claude Code
无需为每个 Claude Code 任务部署 Adapter。

一个 Herdr Connector 的实例可以暴露多个 session / workspace / pane / Agent。权限由原生参数与配置决定；实例 context 是给调用者看的说明，并不强制权限。

读取
agent.read / pane.read 返回终端快照，不能当作完整聊天历史。
启动状态
异步启动可能返回 starting，需按 session + name 查询；超时后进程可能仍在。
代次
当前调用不传 backendGeneration；内部仍用服务代次隔离启动记录和事件订阅。

06 / DEPLOYMENT

一个中继，按运行时部署 Connector

通常每台需要接入的目标电脑安装对应 Connector；Adapter 随 Connector 打包。原生 Agent、模型认证和运行环境分别准备。

01

准备原生运行时

独立安装、认证、启动 Codex app-server / Herdr 等，确认项目、工具和端点可用。

02

部署 Relay

Cloudflare 或单 Linux VPS；配置公网 HTTPS/WSS、管理员密钥与持久存储。

03

配置并配对

按 backend 添加实例；Connector 发起 WSS，所有者核对设备指纹并批准实例范围。

04

授权客户端

支持相应 MCP 的助手连接 Relay /mcp，经 OAuth 授权后发现方法、提交任务与读结果。

部署例子：2 台电脑，3 份 Connector 安装
笔记本
连接 Herdr 与 Codex：两份对应的 Connector。
服务器
连接 Codex：一份 Codex Connector。
共享入口
一个 Relay。每份 Connector 可配置多个实例；20 个 Codex thread 无须安装 20 份 Connector。
数量说明
这是例子，不是固定公式。Paseo / OpenCode 可用远程端点，Lody 自行管理执行主机；Connector 与最终执行机未必一一对应。
谁需要部署什么数量与放置
使用者设备 / 手机使用兼容 MCP 的客户端；Agenvo 本身没有独立手机遥控 App
公共入口个人部署通常一个 Relay；Cloudflare 与 VPS 是两种宿主实现，迁移需重新配对和授权
运行时可访问侧所需 backend 的 Connector；不同 Connector 各自配置目录、配对凭据、锁与服务
每项实例配置内部创建 Adapter 对象；它不是要单独安装的服务
每个原生任务 / 会话使用原生 thread、Agent、pane 等身份；无须再安装 Connector
网络
目标侧主动出站连接 Relay，无须开放公网入站端口；原生本机监听应保持在受保护范围。
准备工作
npm 包不会替你安装 Agent 或模型服务；原生运行时与模型凭据需分别准备。
运行环境
Agenvo：Node.js 24.13+。本站静态网页构建：Node.js 22+。

07 / OBSERVE, THEN DECIDE

提交确认、运行结束、业务成功，是三件事

状态来自原生服务。收到事件后，助手还需要读取证据、检查测试或产物，再决定是否完成。

not_started已知未派发 → 修正条件后重新提交
starting已开始异步操作 → 按返回的查询键观察
accepted原生端接受 → 使用原生 ID 继续读状态
rejected明确拒绝 → 根据原生错误处理
unknown无法确定是否执行 → 先查状态，再决定是否重试写操作

事件只是继续观察的触发器

投递路径
原生变化 → Connector → Relay → 已授权 HTTPS 签名 webhook → 支持 MCP Events 的客户端。
过滤范围
可按 deviceId、instanceId、serviceId、threadId 和原生事件类型过滤。
可靠性
持久保存订阅；事件可能重复、乱序。瞬时失败最多尝试五次，重试沿用事件 ID。
恢复
没有历史重放。收到 agenvo.resync_required 后，重新发现并读取当前状态。
客户端条件
普通 MCP 调用支持不代表事件唤醒可用。dot 跟进还依赖客户端能力、订阅与用户后续指令。

短调用连接长任务

接口时限
execute：30 秒；Relay 原生确认：10 秒；Codex RPC 确认：约 8 秒。均不是整个编程任务的时限。
长任务
提交后返回；调用方等待或接收事件，再用另一调用读结果。脚本没有 sleep / setTimeout，不能在内部忙等。
断线
不会自动重发输入，也不等于取消任务。
取消
Connector 关闭只释放连接，独立原生服务继续运行；需显式调用原生取消能力。
execute 的脚本隔离与返回规则
隔离方式
两种 Relay 共用 QuickJS WebAssembly 模块。宿主可复用引擎模块，每次调用仍创建独立 runtime / context。
可用能力
没有宿主文件、网络、环境变量或模块加载器；脚本通过受控 call 调用原生方法。
原生确认
call 返回 Outcome：execution、requestId、result，以及可选 nativeIds / error。
正常输出
v0.2.0 的 execute 直接交付脚本所选内容：字符串原样返回，其他 JSON 值序列化，没有 return 则为 null。需完整确认时显式 return await call(...)。
异常与写入
脚本失败返回诊断和已派发调用的确认信息；此前写入可能已发生。各调用独立，没有事务、回滚或自动幂等。脚本省略的原生拒绝不会自动把正常 MCP 响应变为 isError。
帧大小
Connector 通信帧通常 64 KiB，解析硬上限 1 MiB；大结果需分页或缩小读取，超限错误可保留 nativeIds。脚本最终输出不经该通道，不能把帧限制套到所有 MCP 输出。
资料依据
事件契约 ↗ 执行器与输出语义 ↗

08 / TRUST BOUNDARIES

自托管带来控制权，也带来维护责任

这些边界决定它适合个人可信环境，还是需要进一步改造。

单所有者

已授权客户端共享获准实例

有效 MCP 客户端可访问全部已批准实例，包括未来批准的实例。当前没有多租户隔离或逐客户端实例 ACL。

运行时权限

脚本隔离不等于执行沙箱

Codex 路径使用 full access / never。Herdr 当前参数原样转发，最终权限由原生 Agent 配置与调用参数决定；工作目录不是安全沙箱。

中继可信

Relay 运维者能看到流量

HTTPS/WSS 保护传输，未提供针对 Relay 运维者的端到端加密。自托管表示你控制中继基础设施，并非无需信任它。

失效与恢复

撤销权限不会取消已有任务

撤销会阻止新访问和在途结果交付；已经开始的原生工作继续运行。设备、实例批准、OAuth grant 和管理员会话分别管理。

授权
OAuth 动态注册 + S256 PKCE；实例范围变更需重新批准。
说明文本
context 是自由文本指导，不能作为实时能力或权限保证。
成熟度
项目仍处早期版本。发行记录与当前源码需分别核对；发布不等于完成独立安全审计。

09 / VALUE TO US

官方能远控了，为什么还看 Agenvo？

先承认功能重叠，再看我们是否需要跨运行时、通用 MCP 接口和可修改的中继。

我们的判断

只为手机继续用 Codex：新增价值有限。
要连接多种 Agent 与自己的系统：值得评估。

价值来自已有接入链和基础设施控制权。原生平台本身也有 API、SDK、MCP 与扩展能力；Agenvo 把这些接入模式做成了可部署的统一入口。

需求官方 Codex 远控 / 接口Agenvo 带来的选择
手机发指令、看进展、继续聊官方远控已支持，受账户、工作区与可用性影响经 MCP 助手调用，额外维护 Relay / Connector；不是独有能力
多主机、通知、查看产物官方支持主机切换、任务通知、输出 / diff / 测试 / 终端等有多实例发现与变化事件；具体读取语义由 Adapter 决定
Codex + Claude Code 等混用官方 Codex 体验主要围绕自身运行时；其他平台各有接入体系同一入口接多类原生服务，助手可以跨实例安排工作
自建助手 / 自动化系统可用 app-server、SDK 等自行接入直接复用 MCP、连接、授权、发现与多个 Adapter，减少接入重复工作
控制接入基础设施使用平台提供的服务与账户体系自托管 Relay，阅读并修改源码；原生模型服务仍需各自凭据
团队权限、可靠任务编排按平台产品能力评估当前单所有者，无统一任务状态和隔离 ACL；需要新设计与验证
场景 A

我们当前主要用 Codex

先用官方远控。只有确实需要另一种 MCP 客户端、跨运行时入口或自建控制流程时，再增加部署。

直接使用价值：较低
场景 B

一个助手管理多种 Agent

例如服务器 Codex 修测试、笔记本 Herdr 中的 Claude 分析方案，由助手分别读取证据、继续推进。

集成价值：较高
场景 C

学习或开发 Agent 平台

研究原生接口适配、长连接路由、请求关联、权限批准、事件恢复和故障语义；可作为接入层参考。

研究与二次开发价值：较高

10 / WHERE TO EXTEND

先补可观测与验收，再扩展任务编排

下面是我们的扩展建议，全部标为“待设计 / 待验证”。它们不是当前库已经具备的功能。

优先 01

连接状态与证据面板 待实现

把 device / instance / 原生会话、断线、授权变更和调用 requestId 展示在一起；关联原生 ID、产物和测试结果。当前管理页侧重设备、实例与授权，尚非完整任务控制台。

优先 02

客户端验收与部署维护 待验证

验证真实 MCP 客户端的工具发现、OAuth、事件订阅与唤醒；补跨平台安装诊断、升级回退流程。search 已有正式版本提示，不能把“提示更新”当成自动升级。

优先 03

新的原生 Connector 待适配

为具备受支持 API / SDK / CLI / 事件接口的运行时实现配置 schema、Backend、methods/call、Outcome 与事件桥接。先保留原生身份和语义，再考虑用户体验统一。

进阶 04

上层任务编排与结果验收 待设计

在调用方构建步骤依赖、Agent 分工、预算与验收记录；等待放在请求之间。由原生状态和产物判定完成，避免把 accepted / idle 当作成功。

进阶 05

不确定执行与恢复策略 待设计

原生服务支持幂等键时才使用去重；unknown 后先对账，保留人工处理路径。事件消费者处理重复、乱序和 resync。端到端“恰好一次”需要新契约，现有 requestId 不足以保证。

进阶 06

权限、团队与隔离 需架构改造

设计逐客户端实例 / 方法授权、租户隔离、独立系统用户或容器、审计与可选审批策略。若要消除中继信任，还需重新设计端到端加密与发现 / 授权关系。

对我们的优先顺序：

先完成真实客户端 + 原生运行时的一次端到端验收，记录提交、断线恢复、结果读取与业务验证，再决定是否构建多 Agent 编排。本站完成的是研究整理与静态网页发布。
