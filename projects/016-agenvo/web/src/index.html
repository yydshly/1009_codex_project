02 / WHAT IT DOES

把远处的 Agent，变成助手可调用的工具

人说目标，助手选择运行位置和原生方法。可用动作取决于对应运行时，能力不会因为接入 MCP 就自动一致。

01

发现与选择

列出获准实例，查看在线状态、原生方法、执行环境说明，选择电脑与运行时。

search · instance context
02

创建与发任务

创建 Codex thread，或在 Herdr pane 启动 Agent，再把提示词送入原生工作上下文。

thread/start · agent.start
03

看进展与结果

读当前状态、原生输出、可用历史或终端快照，判断实际工作进度。

thread/read · agent.read
04

继续与纠偏

恢复会话、追加指令、调整活跃轮次，按运行时提供的能力继续处理。

thread/resume · turn/steer
05

回答与中断

处理用户问题与工具请求，或请求停止。Codex 的精确 turn 中断与终端按键语义不同。

requests.respond · turn/interrupt
06

变化后再跟进

支持事件的 MCP 客户端收到变化后，再读状态、解释结果并决定下一步。

runtime.changed
“协调”发生在上层助手。

Agenvo 没有独立业务任务队列、统一完成判定或自动任务调度器。跨 Agent 分工、重试策略、结果验收由调用方实现。

03 / WHO OWNS WHAT

四个角色，三类状态

适配器是 Connector 里的代码。Relay 是你自托管的公网服务；目标电脑只需主动向它建立连接。

A

客户端 / 上层 AI 助手

接收目标，通过 MCP 发现方法与调用工具；决定任务放在哪里、何时再观察、是否继续或取消。

决策与工作流
B

Relay / 自托管中继

提供 HTTPS MCP、OAuth、管理页、配对与授权；管理 Connector 连接、关联请求结果、执行短脚本、投递事件。

授权与连接状态
C

Connector + 内置 Adapter

通常运行在目标电脑，主动 WSS 连接 Relay。每个配置实例创建一个 Adapter，按实例 ID 分发并翻译成原生调用。

原生连接与桥接
D

真实 Agent / 原生运行时

Codex app-server、Herdr、Paseo daemon 等使用自己的身份、模型凭据、项目、工具、权限与会话历史执行工作。

05 / NATIVE INTEGRATIONS

Codex 是技术接口，Claude Code 经原生管理器接入

不同 Adapter 使用不同接入方式。Agenvo 依赖已有原生能力，把网络、授权、发现和调用链补齐。

原生双向 JSON-RPC

先独立运行 app-server，Connector 再连接

当前实现通过 Unix socket 上的 WebSocket或 loopback WebSocket附着 Codex app-server。Windows 使用 loopback；Connector 不启动或停止 Codex 进程。

连接后 initialize → initialized，核对服务报告的 codexHome 与配置；生成 RPC id、记录 pending，按应答 ID 匹配。通知和待响应请求分别处理。

原生 thread/start 创建会话，turn/start 带 threadId 提交输入。未加载会话先 resume，再操作；返回 turnId 用于后续定位。

当前 Windows / loopback 路径示例

# 原生服务：由另一个终端或服务管理器持有
codex app-server --listen ws://127.0.0.1:4500

# Connector 指向已存在的 home 和服务
agenvo-codex-app-server instance add \
  --id coding --home /existing/codex-home \
  --endpoint ws://127.0.0.1:4500 --cwd /project

命令为说明性示例；Windows 将路径改为实际本机路径、按 PowerShell 语法换行。Node.js 要求 24.13+。

桌面 App 的已有聊天不会自动被接管。

Connector 共享的是所连接端点可访问的会话。另开 app-server 是另一个服务；桌面 stdio 进程没有自动提供兼容监听端点。原生 stdio 接口仍存在，但当前 Agenvo Codex Connector 使用附着模式。

创建、恢复、输入使用 full access / never；原生执行权限请求自动回答，用户问题和动态工具调用仍需内容。原生 schema 包含 experimental 能力，方法可发现不等于在所有版本中可用。通知是连接内有界缓存；历史读取取决于原生服务支持。

原生 CLI + Socket 事件

用 session 找服务，用 name / paneId 找 Agent

Herdr 是独立运行的终端 Agent 管理服务，可管理 Claude Code、Codex 等。Agenvo 附着其实际配置目录，发现 default 与 sessions 内的服务，也能发现外部客户端创建的 Agent。

操作主要执行原生 Herdr CLI。Adapter 把 agent.prompt 转成 herdr agent prompt NAME TEXT，并通过环境变量指向正确服务；CLI 再与原生服务通信。事件订阅直接走原生 socket。

agent.start 在已有 pane 启动进程，由 Herdr 判断 kind；args 原样转发，当前 Agenvo 不维护类型白名单、不注入固定权限参数。

绑定原生 Herdr 服务

HERDR_SOCKET_PATH = session 对应的 socket
HERDR_CONFIG_PATH = configRoot/config.toml
XDG_CONFIG_HOME   = configRoot 的父目录
HERDR_SESSION    = 当前原生 session

agent.prompt({ session, name, text })
→ herdr agent prompt NAME TEXT
→ 原生服务 → 对应 pane 里的 Claude Code
无需为每个 Claude Code 任务部署 Adapter。

一个 Herdr Connector 的实例可以暴露多个 session / workspace / pane / Agent。权限由原生参数与配置决定；实例 context 是给调用者看的说明，并不强制权限。

agent.read / pane.read 是终端快照，不等于完整聊天历史。异步启动可能返回 starting，需按 session + name 查询；超时后进程可能仍在。当前调用不传 backendGeneration；内部仍用服务代次隔离启动记录与事件订阅。

06 / DEPLOYMENT

一个中继，按运行时部署 Connector

通常每台需要接入的目标电脑安装对应 Connector；Adapter 随 Connector 打包。原生 Agent、模型认证和运行环境分别准备。

01

准备原生运行时

独立安装、认证、启动 Codex app-server / Herdr 等，确认项目、工具和端点可用。

02

部署 Relay

Cloudflare 或单 Linux VPS；配置公网 HTTPS/WSS、管理员密钥与持久存储。

03

配置并配对

按 backend 添加实例；Connector 发起 WSS，所有者核对设备指纹并批准实例范围。

04

授权客户端

支持相应 MCP 的助手连接 Relay /mcp，经 OAuth 授权后发现方法、提交任务与读结果。

例：2 台电脑 + 3 类原生运行时

笔记本接 Herdr 和 Codex，服务器接 Codex：通常部署 1 个 Relay + 3 份 Connector 安装。各 Connector 可配置多个实例；Codex 里的 20 个 thread 不需要 20 份 Connector。

这是部署例子，不是数量公式。一个电脑可有多个独立安装；Paseo / OpenCode 等允许远程端点，Lody 的执行主机也由它自身管理，因此 Connector 未必与最终执行机一一对应。

谁需要部署什么数量与放置
使用者设备 / 手机使用兼容 MCP 的客户端；Agenvo 本身没有独立手机遥控 App
公共入口个人部署通常一个 Relay；Cloudflare 与 VPS 是两种宿主实现，迁移需重新配对和授权
运行时可访问侧所需 backend 的 Connector；不同 Connector 各自配置目录、配对凭据、锁与服务
每项实例配置内部创建 Adapter 对象；它不是要单独安装的服务
每个原生任务 / 会话使用原生 thread、Agent、pane 等身份；无须再安装 Connector

目标电脑不需要向公网开放入站端口，需能主动出站连接 Relay；原生运行时的本机监听应保持在受保护的本机范围。npm 包不会替你安装 Agent 或模型服务。Agenvo 需要 Node.js 24.13+，本站静态构建需要 Node.js 22+。

07 / OBSERVE, THEN DECIDE

提交确认、运行结束、业务成功，是三件事

状态来自原生服务。收到事件后，助手还需要读取证据、检查测试或产物，再决定是否完成。

not_started已知未派发 → 修正条件后重新提交
starting已开始异步操作 → 按返回的查询键观察
accepted原生端接受 → 使用原生 ID 继续读状态
rejected明确拒绝 → 根据原生错误处理
unknown无法确定是否执行 → 先查状态，再决定是否重试写操作

事件只是继续观察的触发器

原生变化 → Connector → Relay → 已授权的 HTTPS 签名 webhook → 支持 MCP Events 的客户端。过滤可指定 deviceId、instanceId、serviceId、threadId 和原生事件类型。

Relay 持久保存订阅，但事件可能重复、乱序；瞬时失败最多尝试五次，重试沿用事件 ID。没有历史重放，收到 agenvo.resync_required 应重新发现、读取当前状态。

普通 MCP 调用支持不代表客户端支持事件唤醒。dot 自动跟进还取决于客户端能力、订阅和用户的后续处理指令。

短调用连接长任务

execute 脚本上限 30 秒；Relay 原生确认上限 10 秒；Codex RPC 确认约 8 秒。这些是接口保护时间，不能当作整个编程任务的时限。

提交后及时返回；调用方等待或接收事件，再用另一次 execute 读结果。脚本没有 sleep / setTimeout，不能在内部忙等任务完成。

断线不会自动重发输入，也不等于任务取消。当前 Connector 关闭只释放连接，独立原生服务继续运行；取消需显式调用原生能力。

execute 的脚本隔离与返回规则

两种 Relay 共用 QuickJS WebAssembly 模块，同一宿主可复用引擎模块，但每次创建独立 runtime/context。脚本没有宿主文件、网络、环境变量或模块加载器；它通过受控 call 调用原生方法。

脚本中的 call 返回 Outcome，包含 execution、requestId、result 和可选 nativeIds/error。v0.2.0 正常 execute 响应直接交付脚本所选内容：字符串原样返回，其他 JSON 值序列化，没有 return 则为 null。需要完整确认时显式 return await call(...)。

脚本失败会给出诊断与已派发调用的确认信息；前面的写入可能已经发生。各调用独立，没有事务、回滚或自动幂等。被脚本省略的原生拒绝也不会自动让正常 MCP 响应变成 isError。

原生 Connector 通信帧通常为 64 KiB，解析硬上限 1 MiB。大结果需分页 / 缩小读取，nativeIds 可在超限错误中保留。脚本最终返回内容不经过这条 Connector 通道，不能把帧限制套到所有 MCP 输出上。

08 / TRUST BOUNDARIES

自托管带来控制权，也带来维护责任

这些边界决定它适合个人可信环境，还是需要进一步改造。

单所有者

已授权客户端共享获准实例

有效 MCP 客户端可访问全部已批准实例，包括未来批准的实例。当前没有多租户隔离或逐客户端实例 ACL。

运行时权限

脚本隔离不等于执行沙箱

Codex 路径使用 full access / never。Herdr 当前参数原样转发，最终权限由原生 Agent 配置与调用参数决定；工作目录不是安全沙箱。

中继可信

Relay 运维者能看到流量

HTTPS/WSS 保护传输，未提供针对 Relay 运维者的端到端加密。自托管表示你控制中继基础设施，并非无需信任它。

失效与恢复

撤销权限不会取消已有任务

撤销会阻止新访问和在途结果交付；已经开始的原生工作继续运行。设备、实例批准、OAuth grant 和管理员会话分别管理。

OAuth 使用动态注册与 S256 PKCE；实例范围变更需重新批准。context 是自由文本指导，不是实时能力或权限保证。项目仍处于早期版本；发布记录比未同步的“尚未发布”文档更准确，发行与独立安全审计是不同事实。

09 / VALUE TO US

官方能远控了，为什么还看 Agenvo？

先承认功能重叠，再看我们是否需要跨运行时、通用 MCP 接口和可修改的中继。

我们的判断

只为手机继续用 Codex：新增价值有限。
要连接多种 Agent 与自己的系统：值得评估。

价值来自已有接入链和基础设施控制权。原生平台本身也有 API、SDK、MCP 与扩展能力；Agenvo 把这些接入模式做成了可部署的统一入口。

需求官方 Codex 远控 / 接口Agenvo 带来的选择
手机发指令、看进展、继续聊官方远控已支持，受账户、工作区与可用性影响经 MCP 助手调用，额外维护 Relay / Connector；不是独有能力
多主机、通知、查看产物官方支持主机切换、任务通知、输出 / diff / 测试 / 终端等有多实例发现与变化事件；具体读取语义由 Adapter 决定
Codex + Claude Code 等混用官方 Codex 体验主要围绕自身运行时；其他平台各有接入体系同一入口接多类原生服务，助手可以跨实例安排工作
自建助手 / 自动化系统可用 app-server、SDK 等自行接入直接复用 MCP、连接、授权、发现与多个 Adapter，减少接入重复工作
控制接入基础设施使用平台提供的服务与账户体系自托管 Relay，阅读并修改源码；原生模型服务仍需各自凭据
团队权限、可靠任务编排按平台产品能力评估当前单所有者，无统一任务状态和隔离 ACL；需要新设计与验证
场景 A

我们当前主要用 Codex

先用官方远控。只有确实需要另一种 MCP 客户端、跨运行时入口或自建控制流程时，再增加部署。

直接使用价值：较低
场景 B

一个助手管理多种 Agent

例如服务器 Codex 修测试、笔记本 Herdr 中的 Claude 分析方案，由助手分别读取证据、继续推进。

集成价值：较高

10 / WHERE TO EXTEND

先补可观测与验收，再扩展任务编排

下面是我们的扩展建议，全部标为“待设计 / 待验证”。它们不是当前库已经具备的功能。

优先 01

连接状态与证据面板 待实现

把 device / instance / 原生会话、断线、授权变更和调用 requestId 展示在一起；关联原生 ID、产物和测试结果。当前管理页侧重设备、实例与授权，尚非完整任务控制台。

优先 02

客户端验收与部署维护 待验证

验证真实 MCP 客户端的工具发现、OAuth、事件订阅与唤醒；补跨平台安装诊断、升级回退流程。search 已有正式版本提示，不能把“提示更新”当成自动升级。

优先 03

新的原生 Connector 待适配

为具备受支持 API / SDK / CLI / 事件接口的运行时实现配置 schema、Backend、methods/call、Outcome 与事件桥接。先保留原生身份和语义，再考虑用户体验统一。

进阶 04

上层任务编排与结果验收 待设计

在调用方构建步骤依赖、Agent 分工、预算与验收记录；等待放在请求之间。由原生状态和产物判定完成，避免把 accepted / idle 当作成功。

进阶 05

不确定执行与恢复策略 待设计

原生服务支持幂等键时才使用去重；unknown 后先对账，保留人工处理路径。事件消费者处理重复、乱序和 resync。端到端“恰好一次”需要新契约，现有 requestId 不足以保证。

进阶 06

权限、团队与隔离 需架构改造

设计逐客户端实例 / 方法授权、租户隔离、独立系统用户或容器、审计与可选审批策略。若要消除中继信任，还需重新设计端到端加密与发现 / 授权关系。

对我们的优先顺序：

先完成真实客户端 + 原生运行时的一次端到端验收，记录提交、断线恢复、结果读取与业务验证，再决定是否构建多 Agent 编排。本站完成的是研究整理与静态网页发布。
