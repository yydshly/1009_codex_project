# 003 · Oil UI 研究记录

## 基线与范围

研究来源为 [oil-oil/oil-ui](https://github.com/oil-oil/oil-ui)，固定提交 [`7987bb38afeea1ff8e96641b3ffebb5601fe67d2`](https://github.com/oil-oil/oil-ui/tree/7987bb38afeea1ff8e96641b3ffebb5601fe67d2)，版本 v0.18.0，研究日期 2026-10-09。许可为 MIT，版权归 oil-oil。运行环境为 Windows、PowerShell、Node 22.15.0、Python 3.10.11；子项目不安装 npm 依赖。

研究重点是机制：它如何限制 AI 的决策、怎样定义正确与优秀、怎样把工作分阶段。本项目没有用对照实验证明 Skill 的提升幅度。

## 研究结论速读

- **能力定位：**主要是 AI 前端设计的决策流程与辅助工具，覆盖探索、比较、实现指导、取证和评审。具体实现能力来自宿主模型、素材与项目技术栈。
- **对我们的价值：**研究如何把专家判断转成可执行步骤，安排发散与收敛，让设计决定和修改有依据可查。
- **创意边界：**差异检验可能推动探索；过早固定表达、按同一种审美评分反复修改，也可能排除好方案。后者是我们的机制推断，未测量影响。
- **与 3D 项目的关系：**Oil UI 偏重设计决策，Dioramas 另有资产与渲染引擎，Dvor 提供具体作品及风格化代码。方法和技术工具可以组合。
- **研究状态：**已验证本地工作台操作与部分工具产物；没有对照实验、独立审美评分或质量提升幅度。

完整讨论见下文第 10 节，网页对应 `#summary`。

## 1. 能力

能力包括新界面方向探索、风格和版式比较、视觉润色、截图还原、界面评审，以及动效与素材的设计指导。交付可以是设计说明、小样或可运行页面。实际实现由宿主模型和项目技术栈承担，看图、操作、素材生成和隔离评审能力会影响可完成的范围。

它主要负责设计判断；业务数据流、状态正确性、组件归属、测试与代码架构由项目保障。完整的复杂交互、存量项目改造和组件精修实践主要列在 Pro 中。

依据：[SKILL.md](https://github.com/oil-oil/oil-ui/blob/7987bb38afeea1ff8e96641b3ffebb5601fe67d2/SKILL.md) 与 [README](https://github.com/oil-oil/oil-ui/blob/7987bb38afeea1ff8e96641b3ffebb5601fe67d2/README.md)。

## 2. 底层原理与架构

核心为宿主读取和执行的文本流程。主文件进行范围路由，相关参考文件提供设计方法、视觉规则、评审条件；Agent 调用文件、浏览器和看图能力生成产物并修正。仓库没有负责强制推进阶段的独立状态机。

研究归纳为五层：

1. 输入层：用户任务、品牌、参考、设备与交付形式。
2. 协议层：范围判断、设计方向、视觉语言、动效与验收要求。
3. 执行层：宿主模型、项目代码、文件和浏览器能力。
4. 产物层：方向卡、配置、HTML 对比页、图片、录屏与报告。
5. 反馈层：用户选择、评审意见、修改与交付记录。

这是一种说明仓库责任的分层，不是上游声明的运行时架构。

| 关键文件 | 机制 |
| --- | --- |
| `SKILL.md` | 决定适用路径、阶段顺序和交付条件 |
| `references/design-direction.md` | 以品类和标杆约束方向，要求具体设计决定与差异检验 |
| `references/visual-language.md` | 层级、字体、空间、色彩与控件语言 |
| `references/visual-review.md` | 规定独立评审者收到什么、不得收到什么 |
| `references/reviewer-manual.md` | 缺陷与评分锚点，存量界面按现有规范评审 |
| `scripts/build_style_cards.py` | 校验共用内容与 4–6 张卡片配置，再渲染和组装 |
| `scripts/build_explorer.py` | 校验 manifest、内嵌本地资源、生成便携 HTML |
| `scripts/shoot.mjs` | 启动临时浏览器，通过 CDP 获取截图、交互与动画证据 |

CDP 工具使用 Node 内置 WebSocket 连接浏览器，发送 `Runtime.evaluate`、`Page.captureScreenshot` 和 `Page.startScreencast` 等指令。录屏合成需要 ffmpeg，缺少时可以保留三帧。基础报告包含加载错误、溢出和部分动画探测。

## 3. 约束如何生效

需要区分文本协议与程序限制。前者依赖 Agent 语义执行，后者能通过异常拒绝不合格输入。

| 约束 | 做法 | 强度 |
| --- | --- | --- |
| 范围 | 区分探索、润色、还原、评审和小改动，用户既定要求优先 | 文本协议 |
| 理由 | 写出产品、受众、任务、标杆和保留/改变依据 | 文本协议 |
| 表达 | 将“高级、简洁”等词转为可观察的字体、密度、间距与颜色用途 | 文本协议 |
| 差异 | 未选风格时，骨架、字体、色彩、主视觉至多一项相同；选风格后字体配色固定 | 文本协议 |
| 时序 | 默认先风格卡片、再版式方案、最后完整实现；有明确例外 | 文本协议 |
| 评审 | 只提供当前画面、任务与硬约束，隔离制作过程和旧分数 | 文本协议 |
| 卡片输入 | 4–6 张、必填内容、颜色格式、字体名和控件参数 | 生成器强制校验 |
| 资源输入 | 路径限制、候选类型、必填字段、本机 URL、默认禁用候选脚本 | 生成器强制校验 |
| 页面问题 | 控制台、溢出、图片与动画探测写入报告 | 程序检查，仍需读取和判断 |

文本中写“必须”并不等于代码层面的阶段门禁。尤其截图工具发现页面问题时仍可能返回 0；验收必须读取报告，不能仅凭退出码。这个行为由工具末尾的报告逻辑确认，并在本次首次截图的 favicon 404 中实际观察到。

依据：[方向方法](https://github.com/oil-oil/oil-ui/blob/7987bb38afeea1ff8e96641b3ffebb5601fe67d2/references/design-direction.md)、[卡片生成器](https://github.com/oil-oil/oil-ui/blob/7987bb38afeea1ff8e96641b3ffebb5601fe67d2/scripts/build_style_cards.py)、[对比生成器](https://github.com/oil-oil/oil-ui/blob/7987bb38afeea1ff8e96641b3ffebb5601fe67d2/scripts/build_explorer.py)、[截图脚本](https://github.com/oil-oil/oil-ui/blob/7987bb38afeea1ff8e96641b3ffebb5601fe67d2/scripts/shoot.mjs)。

## 4. 正确与优秀如何定义

正确的基线随任务变化：新界面看任务与用户约束，润色老项目看现有规范，截图还原看参考图。基础门槛包括可读、操作链成立、保存读回、失败保留信息，以及结论有实际证据。

优秀主要由产品适配、表达一致、视觉组织、辨识度与同类完成度组成。上游允许安静、喧闹、精致、粗粝等不同调性，要求取舍来自产品。字号建议是起点，不能替代真实内容与目标视口检查。

评审锚点：8 分要求方向鲜明、流程走通且关键视觉达到同类一线；9 分要求流程、异常状态与细节成立，至少一处达到品类最好；10 分要求没有可观察缺陷，并有品类中未见过的好做法。用户判断优先，不同模型的分数不直接比较。老项目润色不打分，以规范对齐为准。

标准包含作者偏好，例如辨识度、装饰减法与动效证据要求；并非一个客观美感函数。本地演示不引用未经独立评审的分数。

依据：[视觉语言](https://github.com/oil-oil/oil-ui/blob/7987bb38afeea1ff8e96641b3ffebb5601fe67d2/references/visual-language.md)、[评审手册](https://github.com/oil-oil/oil-ui/blob/7987bb38afeea1ff8e96641b3ffebb5601fe67d2/references/reviewer-manual.md)。

## 5. 从零到有的控制

一般路径为：确定任务 → 品类与标杆 → 4–6 张风格卡片 → 2–3 个版式小样 → 记录选定约定 → 代表页实现 → 实际取证 → 评审、减法与交付。

每一步限制下一步的自由度：风格选择固定字色，版式选择固定结构，设计说明保留任务和状态，评审只能在当前目标与硬约束内提出修改。已有参考、只要单方向或授权直接做时，按上游例外减少选择轮次。

本地 `experiment/design-contract.json` 和 `decision-log.json` 记录了工作台的任务、选择、产物、视口、状态与证据要求；网页“从零到有的控制”逐阶段解释输入、约束、产物与检查点。这些记录不是自动执行的状态机。

## 7. 实际场景实验

场景来自当前仓库本身：维护多个 GitHub 研究项目，需要查找项目、读取来源、记录问题和判断。

采用“档案纸张 × 研究桌面”的方向，暖白背景、深绿行动色、衬线展示字和系统正文。桌面采用左队列右详情，手机纵向排列。核心内容是项目对象，主要动作是保存笔记。

执行记录：

- 读取真实 `projects.json`，构建静态快照。它可能随其他项目维护更新，截图是研究时点的证据。
- 通过原始 `build_style_cards.py` 生成 4 张风格卡片；其严格 schema 拒绝不符合约定的配置。
- 在字体和配色固定后制作队列与详情、目录网格、单列档案 3 个小样，再通过原始 `build_explorer.py` 组装。
- 自主选择档案纸张和队列/详情，明确不是用户选择记录。
- 实现搜索、状态筛选、项目选择、空结果、本机笔记、保存读回、失败提示与 JSON 导出。
- 实现首次出场、详情切换和保存操作反馈；尊重减少动态效果的系统偏好。

本实验未完成外部竞品视觉标杆拆解，未独立审美评审，不能声称完整执行所有新设计协议。它是一份可操作的方法演示，并保留过程产物。

## 8. 验证与限制

验证结果写入 `assets/verification.json` 并由网页读取。程序测试覆盖搜索与状态组合、保存读回、存储失败、假写入和损坏存储。浏览器走查覆盖项目切换、空结果、刷新读回和注入失败，截图覆盖桌面与手机。

实际浏览器检查发现空结果处理递归，已修正；首次上游截图工具报告 favicon 缺失，已补显式图标。完成后的检查结果以最终验证记录为准。

最终桌面与手机截图报告无控制台错误、横向溢出和图片加载失败。动效探测确认出场和详情变化；滚动叙事缺失的提示不适用于当前工具型工作台。动效探测的清理阶段在 Windows 遇到临时目录 EBUSY。首次出场录屏首次仅有一帧，第二次无画面，不能当作完整出场证据；独立出场录像仍有缺口。项目切换和保存录像已用 ffprobe 验证有效时长，并实际查看关键帧。

笔记只保存在当前浏览器，未接入 GitHub 账号、后端或同步；项目快照不会自动实时更新。网页扩展方向为研究建议，不是现有功能。

## 9. 使用与扩展

适用场景包括新产品方向探索、现有页面视觉改善、截图还原、只读评审、品牌与关键组件设计。

可扩展为设计约定 schema、显式阶段门禁、团队参考库、工程与可访问性联合验收、绑定截图版本与规则编号的评审记录。这些扩展将部分文本约束转为可检查条件，但审美判断仍应保留任务上下文和用户决策。

## 10. 对我们的价值、创意边界与 3D 对照

### 能力定位与可复用价值

Oil UI 的控制覆盖生成前、生成中和生成后。生成前明确任务、品类与方向；生成中比较候选、记录选择并保持一致；生成后通过实际画面与操作提出问题和修改。它让设计过程更具体、可复查，最终效果仍由模型、素材、工具与人的判断共同决定。

对于本仓库“研究如何从零控制出优秀效果”的目标，我们优先提取以下方法，而非直接采用全部规则：

| 问题 | 可复用的方法 | 应用时的取舍 |
| --- | --- | --- |
| “高级、优秀”难以执行 | 翻译成构图、字体、色彩、密度、动作等选择 | 探索阶段保留不同表达，选定后才固定具体值 |
| 多个候选实际上很相似 | 比较线框、视觉主角与页面结构 | 差异要服务任务，避免增加无用操作 |
| 完整实现后才否定方向 | 先做代表性小样，再选择与扩展 | 小样要暴露核心任务，不能只比较封面 |
| 反复修改导致方向漂移 | 记录选定方向、理由与应保留的记忆点 | 目标改变或方向不适配时允许重开探索 |
| 模型自称完成，缺乏依据 | 绑定实际操作、截图、录屏与具体问题 | 分开记录功能缺陷、视觉缺陷和审美偏好 |

这些是本项目的复用判断；迁移到自建 UI、3D 或创意编程 Skill 后，仍需验证有效性。

### 约束怎样平衡创意

**上游事实：**默认先比较 4–6 张风格卡，再比较 2–3 个版式小样。未锁定风格时，骨架、字体、色彩、主视觉四项中，任意两个方向至多共享一项；选定风格后，字色共享，结构仍要变化。至少一个方向打破品类惯用版式，调性允许时有大胆选择；精修要保留辨识度，集中打磨一两处记忆点。

依据：[设计方向](https://github.com/oil-oil/oil-ui/blob/7987bb38afeea1ff8e96641b3ffebb5601fe67d2/references/design-direction.md)。

**我们的判断：**限制候选相似度可能扩大实际探索，限制过早实现可能降低方向试错成本；但卡片预设、阶段顺序及动效评分带有作者偏好。过早锁定表达可能排除好方案，反复按统一评分修改可能磨平个性。规则多寡与效果优劣不能直接等同，当前没有测量这些影响。

建议按任务区分：正确性设置硬门槛；审美保持可讨论。保存可靠、操作可恢复、文字可读等条件固定；构图、材质、色彩、镜头与交互隐喻在探索阶段开放。动效数量、滚动叙事等要求按产品目标取舍，完成度、独特性、使用代价分别评价。

上游动效要求和评分依据：[评审手册](https://github.com/oil-oil/oil-ui/blob/7987bb38afeea1ff8e96641b3ffebb5601fe67d2/references/reviewer-manual.md)。以上调整是研究建议，未修改上游 Skill，也未安装新的 Skill。

### 与已有 3D 研究的对照

对照使用本仓库已研究的固定提交：Dioramas `868539fb5b64a843071a2247d5d8bacb706a07b1`，Dvor `30d6f684670915865743c79f44f931a43d987113`。

| 项目 | 主要提供什么 | 效果怎样形成 |
| --- | --- | --- |
| Oil UI | 设计决策、方案比较、评审与证据方法 | 组织方向选择与修改，实现由模型、资产和技术工具支撑 |
| Dioramas | 资产生成流程、3D 引擎、交互编排及构建评审方法 | 生成资产与光照、材质、后处理、镜头、交互共同组成场景 |
| Dvor | 具体漫游作品、程序化场景与风格化渲染代码 | 作者布局、统一配色、色带光照、描边及环境叙事形成作品 |

Dioramas 同时包含方法和技术能力，不能把它概括成只有渲染。Dvor 是作者确定方向、通过 AI 辅助编码完成的具体作品，不是通用的优秀 3D 自动生成器。Oil UI 支持用实时 3D 承担检视、物理交互和材质表现；它没有提供相当于上述引擎的运行时代码。

依据：[Dioramas README](https://github.com/blendi-remade/dioramas/blob/868539fb5b64a843071a2247d5d8bacb706a07b1/README.md)、[Dvor README](https://github.com/amirmushichge/dvor/blob/30d6f684670915865743c79f44f931a43d987113/README.md)、[Oil UI 实时 3D 指引](https://github.com/oil-oil/oil-ui/blob/7987bb38afeea1ff8e96641b3ffebb5601fe67d2/references/media.md)。本地细节见 [Dioramas 研究](../002-dioramas/research.md) 与 [Dvor 研究](../004-dvor/research.md)。这是责任和机制对照，未进行跨项目质量排名。

### 迁移到离心泵讲解场景

以下是待执行的迁移方案：

1. 固定任务条件：部件标注准确、拆解关系清楚、操作可恢复、信息可读。
2. 探索工业蓝图、写实展台、风格化实验室等表达，放开镜头、材质、光线和构图。
