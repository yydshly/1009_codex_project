03 / PRINCIPLES

目录怎样工作，作品怎样产生？

Astra 参与开发是创作阶段的信息；浏览器成品是否需要模型，要看各自运行架构。本页轨道花园运行时不调用模型。

目录原理：Markdown 是内容源

  1. 社区整理 README作者提交条目，链接到成品与资料。
  2. 解析与结构化Node 服务用 unified / remark-parse / remark-gfm 读取列表。
  3. 归类、去重、缓存生成稳定标识，整理分类，缓存结果与回退快照。
  4. React 展示与检索界面显示卡片，筛选作品，跳转作者入口。

上游服务采用约 300 秒缓存，刷新按请求触发；前端定期检查更新。这是读取与缓存机制。本地研究页则在构建时解析固定 README，把数据打包进静态文件，浏览时不请求上游目录 API。

创作原理：需求、代码和迭代

  1. 确定需求与约束选择玩法、画面目标、技术栈与操作方式。
  2. Astra 辅助实现生成或修改代码，部分项目另行生成图像素材。
  3. 运行、观察、修正开发者反馈问题，调整规则、性能、画面与交互。
  4. 发布并收录成品部署到网页，社区将链接和说明整理进目录。

条目存在单次生成测试，也存在多轮开发。所选深入案例记录了迭代过程；模型、人工反馈和其他工具的分工应按作者资料说明，不能把整个合集视为一次生成能力证明。

04 / MATURITY

能看到效果，还要判断能用到哪里。

我们的研究判断：成熟度不一，整体偏实验与原型。这里只给证据范围，不为未实测作品编造分数。

可观看 / 可试玩

入口能够展示核心画面或玩法，适合找灵感。仍要检查链接、操作说明、设备兼容和功能是否完整。

可研究 / 可复现

需要源码、运行步骤、依赖和许可；最好同时有 Prompt、改动记录与已知限制。目录提供的资料尚不统一。

还需性能预算、测试、可维护结构、资产许可与部署保障。把这些补齐后，才能按具体业务要求评估。

06 / HOW TO USE

从入口走到自己的可用案例。

  1. 先定问题

    你要理解的是视觉、交互、游戏规则，还是 AI 开发过程？围绕一个具体问题筛选目录。

  2. 筛选证据

    查看平台、作者、模型说明、源码、运行步骤和许可。资料不足的作品可以保留为效果参考。

  3. 运行并记录

    记录固定版本、浏览器和设备；观察核心操作、错误、帧率与重载行为。把可用与失败都写下来。

  4. 做一个小改动

    从换参数、改形态或交互开始，确认效果与代码的因果关系，再决定是否提炼模块。

  5. 形成独立交付

    补齐说明、依赖、测试和许可，保留来源与已知限制；之后按应用的要求再评估。

现在可以做的理解实验

切换“星之花 → 引力环 → 旋涡星系”，观察同一批粒子如何排列；暂停后看几何结构；恢复后释放一次引力，观察扰动与回归。切到“只看背景效果”可以旋转，按 Escape 返回说明。这个实验验证当前案例的交互，不涉及模型调用。

近期 / 实测分层

成熟度与兼容性记录

统一最小运行步骤，检查核心循环、错误、手机、键盘和性能；按可观看、可复现、可复用分层，记录已知缺陷与测试时间。

中期 / 可复用资产

组件与模板提炼

从已验证案例中提取粒子场景、输入、碰撞、声音、状态等模块，提供参数说明、最小示例、许可与边界。

中期 / 对比研究

开发过程与效果关联

保存需求、Prompt、修改轮次和结果，以相同任务与测试环境比较具体方法，区分模型贡献、人工修正和素材工具。

长期 / 持续维护

目录同步与变更追踪

比较上游快照变化，审查后更新；保留测试历史、来源回链与归档状态，避免只累计数量而失去可用性。

长期 / 研究工作台

本质与原理

成熟度边界

成熟度不一，整体偏实验。能试玩不代表稳定可复用；收录不要求开源，功能、兼容性和完整度需逐项验证。此处没有对 175 项进行完整质量评测。

价值

发现创意与交互效果；追溯需求、实现和成品；筛选值得深入的案例。它减少查找成本，后续需要实际验证。

使用场景

学习 AI 辅助编程；小游戏与互动艺术原型；个人作品展示与教学。具体项目的复用仍需检查源码、依赖与许可。
